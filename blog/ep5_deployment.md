## 웹앱(Next.js)에서 네이티브 앱(Capacitor)으로

웹앱이 안정화되면서 피드백이 하나둘 모였습니다. 가장 핵심적인 피드백 두 가지는 이랬습니다.
"매일 아침 푸시 알람이 왔으면 좋겠어요."
"출근길 지하철에서 가끔 끊기는데, 학습 진행도가 저장이 안 돼요."

이 두 가지는 웹 기술(PWA 등)만으로는 완벽히 해결하기 힘든 **"네이티브의 영역"**이었습니다. 그렇다고 처음부터 React Native나 Flutter로 다시 짤 순 없었습니다.

결론은 **Capacitor**였습니다.

Capacitor는 기존 웹 프로젝트를 감싸서 iOS/Android 네이티브 앱으로 만들어주는 도구입니다. teding 같은 구조(Next.js App Router의 SSR + API Routes)에서 기존 코드베이스를 **90% 이상 재사용**하면서 네이티브 기능만 쏙쏙 추가할 수 있는 거의 유일한 대안이었습니다.

하지만 래핑 작업이 단순히 `npx cap sync` 명렁어 한 줄로 끝날 리 없었죠.
몇 가지 치열한 구조 변경이 필요했습니다.

## 인증 이원화: 쿠키와 Bearer의 불편한 동거

웹에서는 Supabase 인증을 쿠키(Cookie) 기반으로 처리하고 있었습니다.
하지만 모바일 앱(WebView)에서는 쿠키가 브라우저 정책(ITP 등)에 의해 종종 막히거나 날아가 버립니다. 모바일은 토큰(Token) 기반 통신이 훨씬 안전합니다.

문제는 **"동일한 API Route를 웹과 앱 양쪽에서 모두 호출한다"**는 점이었습니다. 로그인 여부를 누구는 쿠키로, 누구는 Authorization 헤더로 증명하고 있었죠.

저는 서버 쪽 API 라우트에 `getAuthedClient()`라는 래퍼 함수를 만들었습니다.

```typescript
export async function getAuthedClient(req: Request) {
    const authHeader = req.headers.get("Authorization");
    const token = authHeader?.startsWith("Bearer ") ? authHeader.slice(7) : null;

    // 모바일 앱: HTTP 헤더에 Bearer 토큰이 있으면 그걸로 클라이언트 생성
    if (token) {
        /* ... Bearer 토큰 주입 로직 ... */
        return { supabase, user };
    }

    // 웹 앱: 없으면 기존처럼 cookies() 기반의 서버 클라이언트 반환
    const supabase = await createServerSupabase();
    return { supabase, user: ... };
}
```

이제 웹용 배포(Vercel) 코드는 건드리지 않으면서도, Capacitor 빌드에서는 커스텀 `apiFetch()`를 통해 헤더에 토큰을 실어 보내기만 하면 인증이 통과되었습니다.

## 네이티브 기능 2종: 리젝을 피하는 방법

Google Play Store는 부가가치 없는 단순 WebView 래퍼(껍데기 앱)를 아주 싫어하며 가차 없이 리젝(Reject) 사유로 삼습니다. 심사관을 납득시키려면 웹에서는 불가능한 네이티브 단독의 가치가 있어야 했습니다.

그래서 도입한 것이 **Local Notifications**와 **Offline Queue**입니다.

### 1. 매일 아침 8시의 모닝콜: Local Notifications

FCM처럼 거창한 푸시 서버 인프라를 구축할 필요가 없었습니다. 기기 내부 API를 사용해 "매일 오전 8시마다 같은 알림 띄워줘"라고 스케줄링해버리는 방식입니다. 권한 요청 로직만 추가하면 서버 비용 0원으로 리텐션을 끌어올리는 알림 시스템이 완성됐습니다.

### 2. 에러 400과 500의 차이: 오프라인 진행도 큐잉 (Offline Queue)

제가 가장 공들인 부분입니다.
사용자가 Step 4 학습을 완료하는 순간 연결이 끊긴다면?

무작정 진행 상황을 로컬(Preferences)에 저장해뒀다가 나중에 보내는 단순한 큐잉은 무한 에러 루프를 만들 수 있습니다. HTTP 상태코드 별로 명확한 분류(Triage) 공식을 세웠습니다.

- `TypeError` (네트워크 끊김) ➡️ **큐잉 O** (복구되면 쏜다)
- `5xx` (내 서버가 죽음) ➡️ **큐잉 O** (10번까지만 재시도)
- `401` (세션 만료) ➡️ **큐잉 X** (즉시 드랍 후 로그인 유도)
- `4xx` (요청 잘못됨) ➡️ **큐잉 X** (백날 다시 쏴도 실패함, 드랍)

이 구조 덕에 서버가 잠깐 흔들리거나 터널을 지날 때도 앱은 절대로 뻗거나 렉이 걸리지 않습니다. 인터넷이 연결되는 순간 백그라운드에서 조용히 큐가 비워집니다. 이건 웹에서는 불가능한 압도적인 사용자 경험입니다.
