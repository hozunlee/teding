### 1. AI 생성 학습지의 하이라이트 매칭 불일치 해결

**Problem**
Gemini가 원본 스크립트에서 추출한 핵심표현과, AI가 각색한 학습용 지문(Reading Passage) 텍스트가 미세하게 달라서 UI 하이라이트가 깨지는 현상. 사용자가 지문에서 핵심 구문을 클릭했을 때 아무 반응이 없으면 학습 경험 자체가 무력화됨.

**Analyze — 3가지 대안 검토**

| 대안 | 장점 | 단점 | 판단 |
|---|---|---|---|
| A. 퍼지 매칭(Fuzzy) | 구현 간단 | 오탐률 높음, "a"와 "the" 차이도 다른 문장으로 인식 | ❌ |
| B. AI 후처리 교정 | 정확도 높을 수 있음 | API 호출 2배, 비용·지연 증가 | ❌ |
| C. Passage-First 전략 | 프롬프트 1회로 100% 일치 보장 | 프롬프트 설계 난이도 높음 | ✅ |

**핵심 판단 근거**: 하이라이트는 "비슷하면 되는 것"이 아니라 **토씨 하나도 틀리면 안 되는** 100% 정확도 문제. 후처리 교정은 비용이 2배가 되고 지연이 발생함. 생성 순서를 뒤집어(지문 먼저 → 지문 내부에서만 Verbatim 추출) 아키텍처 레벨에서 문제를 원천 제거하는 것이 가장 근본적인 해결책.

**Action**
- Gemini 프롬프트를 v1(단순 추출) → v2(지문 후 추출) → v3(Passage-First + Verbatim 강제)으로 3회 반복 개선
- `responseMimeType: 'application/json'` 설정으로 마크다운 펜스 파싱 코드 제거
- 단일 API 호출(`/api/generate`)로 worksheet·phrases·sentences를 원자적으로 생성

**Result**
- 하이라이트 매칭률 **0% → 100%** 달성 (Verbatim 일치)
- AI API 호출 횟수 유지 (추가 비용 0)
- 학습지 생성 시간 변동 없음 (프롬프트 구조 변경만으로 해결)

### 2. MVP 4일 달성을 위한 AI 듀얼 페어 프로그래밍 체계 구축

**Problem**
1인 개발로 인증·대시보드·4단계 학습 플로우·AI 파이프라인·Admin까지 구현해야 하는 상황. 전통적 방식이라면 최소 2~3주 소요. AI 코딩 도구를 활용하되, AI 환각(Hallucination)으로 인한 코드 품질 저하를 어떻게 방지할 것인가.

**Analyze — AI 협업 전략 비교**

| 전략 | 장점 | 단점 |
|---|---|---|
| A. 단일 AI + 자유 대화 | 간편 | 컨텍스트 유실, 환각 누적 |
| B. 단일 AI + 문서 기반 | 일관성 확보 | 한 모델의 약점이 전체 품질 한계 |
| C. 듀얼 AI + 문서 기반 오케스트레이션 | 모델별 강점 분담, 교차 검증 | 워크플로우 설계 비용 |

**핵심 판단 근거**: Claude Code는 대규모 리팩토링과 아키텍처 설계에 강하고, Gemini CLI는 빠른 반복과 UI 컴포넌트 생성에 강점. 이 두 모델을 **`docs/` 폴더의 문서 기반 오케스트레이션**으로 묶으면, 세션 간 컨텍스트 유실 없이 각자의 강점을 살릴 수 있음.

**Action**
- **`docs/WORKFLOW.md`**: AI 세션 시작 시 반드시 읽는 규칙서 (태스크 상태 흐름, 제약 조건)
- **`docs/ARCHITECTURE.md`**: 스키마/API 변경 시 즉시 기록 → AI 환각 방지의 SSoT
- **`docs/tasks/TASK_XXX.md`**: 태스크별 목표·맥락·완료 기준 체크리스트
- **`docs/DONE.md`**: 완료 이력 한 줄 요약 (토큰 효율화)
- Claude Code로 DB 설계·인증 아키텍처·API 라우트 초안 생성 → Gemini CLI로 UI 컴포넌트 양산·디자인 시스템 적용·빠른 버그 수정
- 양쪽 모두 동일한 `docs/` 문서를 참조하므로 **세션이 끊겨도 컨텍스트가 문서에 영속화**

**Result**
- **MVP 완성 4일** (04/05~04/09): 인증 → 대시보드 → 학습 4단계 → Admin 전체 구현
- 이후 3주간 **36+ TASK** 완료 (고도화·버그픽스·SEO·앱 패키징)
- AI 환각으로 인한 회귀 버그 **0건** (ARCHITECTURE.md가 SSoT 역할)

### 3. 비로그인 사용자 이탈 방지를 위한 PLG 전환

**Problem**
초기 설계에서는 `AuthGuard`로 모든 학습 페이지를 보호했으나, 신규 사용자가 콘텐츠를 경험하기도 전에 로그인 벽에 막혀 이탈. 교육 앱 특성상 **"이 앱이 가치가 있는지"를 먼저 보여줘야** 전환율이 올라감.

**Analyze — 인증 전략 3가지**

| 전략 | 전환 시점 | 리스크 |
|---|---|---|
| A. 전체 페이지 로그인 필수 | 최초 진입 | 가치 경험 전 이탈률 극대화 |
| B. 1단계만 무료 개방 | Step 1 이후 | 학습 플로우가 끊겨 불만 유발 |
| C. 전체 개방 + 저장 시 유도 | 완료·저장 시점 | 무임승차 가능성 있으나 전환 품질 높음 |

**핵심 판단 근거**: 학습 앱에서 "무임승차"란 **사용자가 실제로 학습을 완료한 것**이므로 사실상 윈-윈. 가치를 충분히 경험한 시점에 로그인을 유도하면 **전환 의지가 가장 높은 순간**을 포착 가능.

**Action**
- `AuthGuard` 제거 → `/admin`만 미들웨어(`proxy.ts`)에서 보호
- Zustand 기반 `useAuthModal()` 전역 스토어 신설
- Step 4 완료 버튼 · 학습 완료 화면 · 최근 기록 클릭 시점에 모달 유도
- `/api/history`는 비로그인 시 401 대신 `{ history: [], loggedIn: false }` 반환 (에러 없는 그레이스풀 처리)

**Result**
- 비로그인 사용자도 Step 1~4 전체 학습 가능 (가치 경험 플로우 100% 개방)
- 로그인 유도 시점을 **"방금 학습을 완료한 순간"**으로 집중 → 자연스러운 전환
- 이탈 없이 콘텐츠 공유 가능 (카카오톡 공유 링크에서 진입한 사용자도 즉시 학습 시작)

### 4. Capacitor를 활용한 웹앱의 네이티브 전환 — Play Store 리젝 방어

**Problem**
학습 알람과 오프라인 학습 기능을 위해 Android 앱이 필요했으나, React Native/Flutter로 재작성하면 기존 웹 코드베이스를 버려야 함. 반면 단순 WebView 래퍼는 Play Store에서 **"부가가치 없는 WebView 앱"**으로 리젝 위험.

**Analyze — 네이티브 전환 전략**

| 전략 | 개발 비용 | 코드 재사용 | Play Store 리젝 위험 |
|---|---|---|---|
| A. React Native 재작성 | 높음 (3~4주) | 0% | 낮음 |
| B. PWA만 활용 | 없음 | 100% | 앱 출시 불가 |
| C. Capacitor + 네이티브 기능 2종 | 중간 (1주) | 90%+ | **낮음 (네이티브 기능 증빙)** |

**핵심 판단 근거**: Play Store 심사의 핵심은 "웹에서 불가능한 네이티브 고유 기능이 있는가". Local Notifications(매일 학습 알람)과 Offline Queue(진행도 큐잉 + 자동 동기화)를 구현하면 네이티브 부가가치를 증빙 가능. 동시에 기존 Next.js 코드의 90% 이상을 재사용.

**Action**
- 인증 이원화: 쿠키(웹) + Bearer 토큰(앱) 동시 지원하는 `getAuthedClient()` 래퍼
- CORS 이중 방어: `next.config.ts headers()` 1차 + `proxy.ts` Preflight 2차
- 오프라인 큐: HTTP 상태코드별 에러 분류 (네트워크 단절/5xx → 큐잉, 4xx/401 → 즉시 드랍)
- Local Notifications: FCM 서버 인프라 없이 디바이스에서 직접 매일 아침 알람 스케줄링
- `output: 'export'`로 웹/앱 빌드 분기, `prebuild:app`에 동적 라우트 자동 검사 스크립트 연결

**Result**
- 기존 웹 코드베이스 **90%+ 재사용**, 앱 전용 코드 약 700줄 추가
- Play Store 리젝 방어를 위한 **네이티브 기능 2종**(알람 + 오프라인) 구현 완료
- 웹 사용자 경험 **무변경** (기존 쿠키 인증 그대로 작동)

## 기술 스택 선정 근거

| 기술 | 선택 이유 |
|---|---|
| **Next.js 16 (App Router)** | SSR + API Routes 통합으로 별도 백엔드 서버 불필요. Static Export로 Capacitor 앱 빌드 가능 |
| **Supabase** | Auth·DB·Storage를 단일 서비스로 통합. RLS로 보안 정책을 DB 레벨에서 선언적 관리 |
| **Gemini 2.5 Flash-Lite** | 학습지 생성에 최적화된 cost 대비 성능. `responseMimeType: 'application/json'`으로 구조화 응답 |
| **Claude (폴백)** | Gemini 장애 시 자동 전환. 프롬프트 호환성 확보 |
| **Capacitor** | 기존 웹 코드 90%+ 재사용. 네이티브 API 접근(알림·오프라인·딥링크) |
| **TailwindCSS + shadcn/ui** | 디자인 시스템 빠른 구축. 시맨틱 토큰으로 다크모드·인쇄 대응 |

## AI 듀얼 개발 체계 상세

### 역할 분담

```
┌─────────────────────────────────────────────────┐
│   docs/ (컨텍스트 허브 — SSoT)                    │
│   ├── WORKFLOW.md     → AI 협업 규칙              │
│   ├── ARCHITECTURE.md → 스키마/API 변경 이력       │
│   ├── tasks/TASK_XXX  → 태스크 명세              │
│   └── DONE.md         → 완료 이력                │
└─────────────────────────┬───────────────────────┘
                          │
              ┌───────────┼───────────┐
              ▼                       ▼
    ┌──────────────────┐    ┌──────────────────┐
    │   Claude Code     │    │   Gemini CLI      │
    │                    │    │                    │
    │ • DB 설계/마이그   │    │ • UI 컴포넌트 양산 │
    │ • 인증 아키텍처    │    │ • 디자인 시스템     │
    │ • API 라우트 설계  │    │ • 빠른 버그 수정   │
    │ • 리팩토링/통합    │    │ • CSS/Tailwind     │
    │ • 앱 패키징 설계   │    │ • SEO/메타데이터   │
    └──────────────────┘    └──────────────────┘
```

### 이 체계가 효과적인 이유

1. **세션 독립성**: AI 세션이 끊겨도 `docs/`에 모든 결정이 영속화되어 있어 새 세션에서 즉시 복구
2. **교차 검증**: Claude Code가 설계한 아키텍처를 Gemini CLI가 구현하면서 자연스럽게 리뷰 효과
3. **환각 방지**: `ARCHITECTURE.md`가 스키마의 단일 진실 소스(SSoT) 역할 → AI가 구버전 구조로 코드 생성하는 것을 방지
4. **토큰 효율화**: `DONE.md`에 한 줄 요약만 남기고, 태스크 파일은 완료 후 `/tasks/done`으로 이동 → 활성 컨텍스트 최소화

## 회고

### 잘한 점
- **문서 기반 AI 오케스트레이션**: `docs/` 폴더가 인간과 AI 모두의 컨텍스트 허브가 되어, 1인 개발임에도 팀 수준의 일관성을 유지

- 초기에 AuthGuard를 먼저 구현했다가 PLG로 전환하면서 불필요한 리팩토링 발생 → 사용자 플로우를 먼저 설계한 뒤 인증 전략을 결정했어야
- 성과 측정 인프라(GA4)를 Day 1부터 설치하지 않아 초기 사용자 행동 데이터 유실
- 테스트 코드 부재 — AI가 생성한 코드의 품질 안전망으로 최소한의 통합 테스트 필요
